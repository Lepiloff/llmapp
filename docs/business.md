# LLM App Market — бизнес-описание продукта

> Документ описывает **что мы строим** и **как продукт должен работать**.
> Сознательно вынесено за скобки: монетизация, маркетинг, go-to-market, ценообразование, конкурентная экономика, найм, расходы.
> Для технической реализации см. [`architecture.md`](./architecture.md).

---

## 1. Продукт и позиционирование

**LLM App Market (llmappmarket.com)** — независимый каталог-навигатор приложений, коннекторов, интерактивных приложений и MCP-серверов, которые расширяют возможности LLM-ассистентов (ChatGPT, Claude, Gemini и совместимых клиентов).

Продукт отвечает на один главный пользовательский вопрос:

> «Какие приложения и интеграции уже существуют для моего AI-ассистента — и какое из них подходит под мою задачу?»

LLM App Market — не «ещё один список AI-tools» и не магазин с покупкой и установкой внутри сайта. Это **discovery-слой**: пользователь приходит, находит нужный инструмент, переходит на официальную страницу платформы (ChatGPT App Directory, Claude Connectors, MCP Registry, Gemini, и т.п.) и устанавливает его уже там.

Ключевые отличия от соседних категорий:

| Категория | Что у них | В чём наше отличие |
|---|---|---|
| Futurepedia / Toolify / There’s An AI For That | Тысячи разрозненных AI-сервисов (генерация картинок, видео, HR, и т.д.) | Узкая ниша — только то, что расширяет LLM-ассистентов |
| Официальные каталоги OpenAI, Anthropic, Google | Только своя экосистема | Кросс-платформенный, нейтральный, сравнительный взгляд |
| Сторонние MCP-каталоги | Узко-технические, для разработчиков | Двухслойная аудитория: и пользователь, и разработчик; объяснения простым языком |

### Подзаголовок продукта

> Discover apps, connectors and agents for ChatGPT, Claude, Gemini and beyond.

### Категориальное обещание

LLM App Market — это **самый понятный кросс-платформенный каталог приложений, коннекторов и MCP-серверов**: одно место, где их можно найти, понять и сравнить вне зависимости от платформы. «Самый свежий» — внутренняя амбиция, измеряемая метрикой freshness (см. § 15.1), а не публичное обещание: новостной охват в стиле Product Hunt мы не закладываем.

## 2. Целевая аудитория

В MVP — три аудитории. Никакие другие в начальный скоуп не входят.

### 2.1. AI power users

Кто это: люди, которые уже ежедневно используют ChatGPT / Claude / Gemini и хотят получить от ассистента больше, чем просто чат.

Их вопросы:

- «Что нового появилось на этой неделе?»
- «Какой connector лучше для управления задачами?»
- «Можно ли подключить ассистента к моему Google Drive / GitHub / Notion?»
- «Что выбрать: ChatGPT App или Claude Connector?»

Что им нужно от продукта:

- Полнотекстовый поиск по задаче, а не по бренду.
- Понятные карточки с человеческим описанием.
- Сравнение похожих инструментов.
- Лента новинок.

### 2.2. Разработчики LLM-приложений и MCP-серверов

Кто это: создатели приложений, коннекторов, серверов MCP, которые ищут новых пользователей.

Что им нужно от продукта:

- Бесплатное базовое размещение.
- Возможность «заявить владение» уже существующей карточкой (claim listing).
- Видимость — рейтинги, подборки, попадание в категорию.
- Уверенность, что страница отражает реальные возможности продукта.

В MVP личного кабинета разработчика нет. Все действия — через публичные формы и ручную модерацию.

### 2.3. Малый бизнес и команды

Кто это: продакт-менеджер, тимлид, маркетолог, основатель — те, кто не хочет читать документацию платформ и сразу ищет «инструмент под задачу».

Их типичные запросы:

- «AI-инструмент для работы с CRM»
- «коннектор для Google Workspace»
- «инструмент аналитики Slack/Notion/Linear через AI»
- «приложение для подготовки слайдов из заметок»

Что им нужно от продукта:

- Категориальные подборки.
- Понятные ярлыки «Read-only», «Can take actions», «Requires login».
- Чек-листы безопасности (verified, requires auth, official).

## 3. Какие задачи решает продукт (jobs-to-be-done)

Продукт сфокусирован на следующих JTBD. Любая фича должна работать на одну из них; всё остальное — вне MVP.

| # | Job | Как продукт решает |
|---|---|---|
| J1 | «Найти инструмент под конкретную задачу» | Поиск по use case + категориальные страницы |
| J2 | «Понять, совместим ли инструмент с моим ассистентом» | Поле *Works with* + фасет *Platform* |
| J3 | «Сравнить альтернативы» | Блок *Similar tools* на странице приложения + comparison-страницы |
| J4 | «Понять, что инструмент реально делает» | Структурированные поля *Capabilities* (read / write / interactive / auth / local / remote) |
| J5 | «Отличить официальный продукт от любительского» | Поле *Verification status* + бейджи на карточке |
| J6 | «Следить за новинками экосистемы» | Лента *Newly added*, *Trending*, weekly digest |
| J7 | «Получить контекст по понятию» | Editorial-материалы («Что такое MCP?», «ChatGPT App vs Claude Connector») |
| J8 | «Опубликовать своё приложение» | Submit listing form |
| J9 | «Заявить владение карточкой» | Claim listing form |

## 4. Скоуп MVP

### 4.1. Что входит в MVP

- Каталог приложений с фасетной фильтрацией.
- Поиск (полнотекстовый, с тайпо-толерантностью).
- Страница приложения с фиксированной анатомией.
- SEO-страницы для платформ, категорий и их комбинаций.
- Editorial-страницы (подборки, объяснялки, сравнения).
- Форма Submit listing (публичная, без аккаунта).
- Форма Claim listing (публичная, без аккаунта).
- Подписка на email-дайджест.
- Outbound-клик-трекинг (на install / official page).
- Sitemap, robots, OpenGraph, JSON-LD.
- Ручная модерация всех публикаций через Django Admin.
- Автоматический ingest публичных MCP-серверов из MCP Registry в очередь черновиков.

### 4.2. Что НЕ входит в MVP (и почему)

| Фича | Почему не сейчас |
|---|---|
| Покупка / установка прямо на сайте | Излишне ранний marketplace, не нужен для discovery |
| Собственный runtime для запуска приложений | Не наша роль; ответственность платформ |
| Платежи, подписки, тарифы | Не приоритет MVP; уводит от продуктовой ценности |
| Пользовательские отзывы и рейтинги | Сначала нужно накопить трафик и аудиторию, иначе спам и накрутки |
| Личные кабинеты разработчиков, OAuth, роли | Заменяется публичными формами + Django Admin |
| Автоматическая публикация без модерации | Гарантия качества листингов важнее скорости |
| Сложные мульти-язычные интерфейсы (i18n) | Первый релиз — на английском |
| Мобильное приложение | Сайт-first, мобильная адаптивная вёрстка достаточно |

## 5. Доменная модель: типы листингов

Карточка в каталоге всегда относится к одному из **типов листингов**. Это не категория, а класс сущности; влияет на отображение карточки и на способ установки.

### 5.1. ChatGPT App

- **Что это**: приложение, опубликованное в ChatGPT App Directory от OpenAI.
- **Установка**: через ChatGPT (в чате или из директории), требует учётной записи OpenAI.
- **Ключевые атрибуты карточки**: official directory URL, required plan (Free / Plus / Pro / Enterprise), регион-ограничения, поддерживаемые модели.
- **Источник данных**: ручной curated + ссылки на официальный directory.

### 5.2. Claude Connector

- **Что это**: проверенная MCP-интеграция, попавшая в Claude Connectors Directory от Anthropic.
- **Установка**: внутри настроек Claude (Web / Desktop / Mobile).
- **Ключевые атрибуты**: directory URL, требуемые scopes, поддерживаемые сценарии (read vs action), наличие интерактивного UI.
- **Источник данных**: ручной curated.

### 5.3. Interactive Claude App

- **Что это**: коннектор, который рендерит полноценный UI внутри чата Claude (доски, графики, дизайн-инструменты).
- **Установка**: как Claude Connector, но с пометкой «interactive UI».
- **Ключевые атрибуты**: тот же набор + флаг `interactive_ui = true`, скриншоты UI.
- **Источник данных**: ручной curated.

### 5.4. MCP Server

- **Что это**: публичный сервер, реализующий Model Context Protocol; используется Claude, ChatGPT (через Apps SDK), Cursor, IDE и другими клиентами.
- **Установка**: зависит от клиента; может быть `remote` (HTTPS endpoint), `local` (npm/pip/uvx-команда), или managed.
- **Ключевые атрибуты**: protocol version, transport (stdio/SSE/HTTP), required env-переменные, open-source-флаг, репозиторий.
- **Источник данных**: автоматический ingest из MCP Registry + submissions.

### 5.5. Gemini Connected App

- **Что это**: приложение или сервис, который Gemini может использовать с разрешения пользователя.
- **Установка**: внутри настроек Gemini / Google Account.
- **Ключевые атрибуты**: required Google scopes, тип интеграции (data access vs action).
- **Источник данных**: ручной curated.

### 5.6. Опционально: Enterprise Agent

- **Что это**: готовый агент или агентный компонент из enterprise-маркетплейсов (Salesforce AgentExchange, Microsoft Agent Marketplace, и т.п.).
- **Зачем**: даёт точку входа для B2B-аудитории.
- **MVP-статус**: добавляется отдельной секцией, без глубокой интеграции. Карточки заводятся вручную.

### 5.7. Когда инструмент относится к нескольким типам

Одно приложение может одновременно быть, например, ChatGPT App **и** MCP Server (Asana, Notion). В этом случае:

- В каталоге это **одна** карточка `App`, привязанная к нескольким `ListingType`-ам.
- На карточке секция *Works with* показывает все варианты использования.
- В фасетах фильтр *Platform* помогает быстро ограничить выборку.

## 6. Структура контента (taxonomy)

Качественная таксономия — главная защита от превращения каталога в «помойку ссылок». Поля карточки фиксированы; всё, что не помещается в структуру, идёт в свободное текстовое поле.

### 6.1. Платформы (фиксированный список)

- ChatGPT
- Claude
- Gemini
- MCP-compatible clients (общий зонтик)
- Enterprise (Salesforce, Microsoft, и т.п. — общий зонтик)

### 6.2. Категории (10 на старте)

1. Productivity & Task Management
2. Developer Tools
3. Research & Knowledge
4. Files & Documents
5. Design & Creative
6. Sales & CRM
7. Marketing & Content
8. Data & Analytics
9. Travel & Local Search
10. Commerce & Shopping

Категория — основа SEO-страниц. Список можно расширять, но не в первый релиз.

### 6.3. Capabilities (флаги)

Каждая карточка проходит чек-лист capabilities. Это структурированные `да / нет / неизвестно` поля:

- `read_data` — может читать данные пользователя
- `write_actions` — может выполнять действия от лица пользователя
- `interactive_ui` — рендерит UI внутри чата
- `auth_required` — требует логин / авторизацию
- `local_setup_required` — требует локальной установки на машине пользователя
- `remote_available` — есть hosted/remote-вариант
- `open_source` — есть публичный исходный код
- `api_available` — есть отдельный API

### 6.4. Pricing model

- `free` — полностью бесплатно
- `paid` — только платно
- `freemium` — есть бесплатный план
- `unknown` — не подтверждено

Отдельно поле `supported_plans` (на каждой связи `App ↔ Platform`): список тарифов платформы, на которых работает интеграция (`Free`, `Plus`, `Pro`, `Business`, `Enterprise`). Хранится массивом — это позволяет показывать пользователю «работает на Plus и выше», а не одно значение.

### 6.5. Trust model — три независимых статуса

Раньше «verification_status» смешивал три разных типа доверия. В MVP они разнесены и хранятся отдельно, потому что отражают разные сущности и не зависят друг от друга:

#### a) `platform_verification_status` — присутствие в официальном каталоге платформы

- `official` — карточка соответствует существующей записи в официальном каталоге (ChatGPT App Directory, Claude Connectors Directory, MCP Registry и т.п.).
- `not_listed` — на платформе официальной записи нет (community-сервер, ранний preview, личный проект).
- `unknown` — мы ещё не сверяли.

Этот статус подтверждается **ссылкой** в `AppPlatform.official_directory_url`. Без ссылки нельзя выставить `official`.

#### b) `editorial_review_status` — что сделала редакция LLM App Market

- `reviewed` — карточку проверил редактор: описание, capabilities, ссылки, скриншоты.
- `unreviewed` — карточка не проходила ручную проверку (например, авто-импорт из MCP Registry в очередь черновиков, ещё не дошедший до редактора).

Этот статус — наша внутренняя ответственность; он не зависит от платформ и от разработчика.

#### c) `developer_claim_status` — кто-то с доменом разработчика заявил права на карточку

- `claimed` — claim прошёл проверку и подтверждён редактором (см. § 10).
- `pending` — claim подан, ждёт ручного подтверждения.
- `unclaimed` — никто не заявлял.

Этот статус относится к карточке, не к платформе. Один и тот же `App` может быть `official` на платформе, но `unclaimed` (разработчик до нас не дошёл), и наоборот: `claimed` коммьюнити-сервер, который ещё не попал в официальный каталог.

#### Бейджи на карточке

На странице приложения показываем эти три статуса разными бейджами:

- Listed on ChatGPT App Directory (platform official)
- Reviewed by LLM App Market (editorial)
- Verified by developer (claim)

Это даёт пользователю возможность видеть **источник** доверия, а не одно слово «official», за которым может стоять что угодно.

Quality Score (§ 12) учитывает все три статуса как независимые слагаемые.

### 6.6. Launch status

- `live` — публично доступно
- `beta` — публичная бета / preview
- `waitlist` — анонсировано, доступ ограничен
- `deprecated` — больше не поддерживается / снято с публикации

### 6.7. Дополнительные поля на связке `App ↔ Platform`

Эти поля живут не на самой карточке `App`, а на связке `AppPlatform`: одно и то же приложение может быть доступно на разных платформах с разными ограничениями. Часть полей универсальна, часть — type-specific (например, поля transport / protocol_version имеют смысл только для MCP-серверов).

Универсальные:

- `scope_summary` — короткое описание того, какие доступы запрашивает интеграция при подключении. Свободный текст, до 280 символов. Пример: «read/write access to your project tasks; cannot delete projects».
- `region_availability` — список регионов, в которых интеграция доступна (`worldwide`, `us_only`, `eu_only`, `excludes_eea`, и т.п.). Пользователь не должен находить инструмент, который потом не работает в его стране.
- `supported_plans` — на каких тарифах платформы доступно (`Free`, `Plus`, `Pro`, `Business`, `Enterprise`).
- `supported_models` — для App-listing-ов внутри ChatGPT/Claude: с какими моделями работает (`gpt-5`, `claude-4-sonnet`, ...). Свободный текст.
- `last_verified_on_platform_at` — когда мы в последний раз сверяли карточку с официальным каталогом платформы.

MCP-специфичные (хранятся в служебном JSON, чтобы не плодить колонки под каждый тип листинга):

- `protocol_version` — версия MCP, против которой сервер заявлен.
- `transport` — `stdio` / `sse` / `http` / `websocket`.
- `repository_url` — публичный репозиторий (если открытый исходный код).
- `required_env_vars` — список ключей переменных окружения, без значений; пользователь видит, что нужно для запуска.
- `install_command` — `npx @scope/server` / `uvx ...` / docker-команда.

ChatGPT- / Claude-специфичные дополнения тоже идут в JSON-поле:

- `marketplace_listing_id` — внешний ID, для backlink-обновлений.
- `auth_provider` — на каком OAuth-провайдере живёт авторизация.

Эти поля нужны не для «галочки», а для двух конкретных пользовательских сценариев:

1. Регион/тариф/модель — «можно ли мне это использовать?»
2. Protocol/transport/repo/env — «как разработчику оценить, подходит ли MCP-сервер технически?»

Без них каталог обещает доверие, которое не может подтвердить.

### 6.8. Use cases

Свободный (но управляемый) словарь коротких фраз: «turn notes into slides», «summarize project backlog», «search files in Google Drive», «query Postgres database», и т.п. Используются:

- в карточке (секция *Use cases*);
- в поиске (попадают в индекс);
- в editorial-страницах (как лейблы подборок).

Редактор может вводить новые use case-метки; дубликаты схлопываются вручную.

## 7. Карта сайта и страницы

```
/                                                  Главная
/apps/                                             Каталог + фасеты
/apps/{slug}/                                      Карточка приложения
/chatgpt-apps/                                     Platform page
/claude-connectors/
/mcp-servers/
/gemini-apps/
/apps/{category-slug}/                             Category page
/{platform-slug}/{category-slug}/                  Cross page (e.g. /claude-connectors/sales-crm/)
/best/{slug}/                                      Editorial podborka (e.g. /best/chatgpt-apps-for-travel/)
/vs/{a}-vs-{b}/                                    Comparison page
/submit/                                           Submit listing form
/claim/{app-slug}/                                 Claim listing form
/blog/                                             Editorial / explainer hub
/blog/{slug}/
/digest/                                           Newsletter подписка / архив
/about/, /privacy/, /terms/                        Статика
```

### 7.1. Главная

Блоки сверху вниз:

1. **Hero** — название продукта, подзаголовок, две CTA: *Browse the directory* и *Submit your app*.
2. **Browse by platform** — 4 крупные ссылки (ChatGPT / Claude / Gemini / MCP).
3. **Browse by category** — 10 категорий из § 6.2.
4. **Trending** — 6–9 самых популярных карточек по outbound-кликам за последние 7 дней.
5. **Newly added** — 6–9 свежедобавленных карточек.
6. **Popular guides** — 3–5 editorial-материалов (что такое MCP, как выбрать app, и т.п.).
7. **Developer CTA** — «Built an LLM app? Get listed for free.»
8. **Newsletter CTA** — подписка на дайджест.
9. Футер.

### 7.2. Каталог `/apps/`

- Левая колонка: фасеты (см. § 8).
- Правая колонка: карточки (карточка-grid, по умолчанию 12 на страницу).
- Сортировка: relevance / newest / featured / quality score.
- Активные фильтры отображаются под заголовком, удаляются одним кликом.
- Пустой результат: блок «Ничего не нашли. Попробуйте...» + 3 популярных запроса.

### 7.3. Страница приложения `/apps/{slug}/`

Зафиксированная анатомия (используется как шаблон для всех карточек):

1. **Header**
   - Логотип, название, developer.
   - Бейджи: тип листинга, verification status, launch status.
   - CTA: *Open in directory* (если есть official URL), *Visit website*, *Claim this listing*.
2. **Verdict** — одно-два предложения от редактора: «Best for X if you want Y.»
3. **What it does** — 3–5 буллетов простым языком.
4. **Works with** — таблица: платформа × `compatibility_status` × required plan.
5. **Capabilities** — таблица флагов из § 6.3.
6. **Use cases** — буллет-список.
7. **How to use / Install** — короткая инструкция, ссылка на официальную доку.
8. **Pricing & access** — `pricing_model`, `auth_required`, `local_setup_required`.
9. **Similar tools** — 3–6 карточек той же категории / типа.
10. **Metadata** — официальный developer, последняя проверка, источник данных.
11. **JSON-LD `SoftwareApplication`** в head — для SEO.

### 7.4. Platform pages

`/chatgpt-apps/`, `/claude-connectors/`, `/mcp-servers/`, `/gemini-apps/`.

Структура одинаковая:

- Hero-объяснение: что это за платформа, как туда попадают приложения.
- Список топ-20 карточек этой платформы (по quality score).
- Подкатегории (cross-link на `/{platform}/{category}/`).
- 3–5 editorial-материалов.
- CTA «Submit your app».

### 7.5. Category pages

`/apps/productivity/`, `/apps/developer-tools/`, и т.д.

Структура:

- Hero: «Best LLM apps for productivity».
- Список карточек категории, отсортированный по quality score.
- Подразделы по платформам (cross-link).
- 1–2 editorial-материала по категории.

### 7.6. Cross-pages

`/claude-connectors/sales-crm/`, `/mcp-servers/developer-tools/`, и т.д.

Авто-генерируемые из существующих пар (платформа × категория). Включаются только если в паре есть минимум 3 опубликованных карточки.

### 7.7. Editorial / comparison

- `/best/{slug}/` — подборка («Best ChatGPT Apps for Travel», «Best MCP Servers for Developers»).

## 8. Поиск и фильтрация (UX-слой)

### 8.1. Что ищется

В индекс поиска попадают:

- `name`
- `short_description`
- `long_description`
- `developer_name`
- `use_cases` (как массив строк)
- `categories` (как массив строк)
- `platforms` (как массив строк)

Поиск применяет typo tolerance (fuzzy match по `name`) и phrase matching по описаниям. Технически реализован на Postgres (см. `architecture.md`), но это деталь реализации — пользователю обещание прежнее: «найди по смыслу, даже если опечатался».

### 8.2. Фасеты

В порядке, в котором они показаны на странице:

1. **Platform** — multi-select.
2. **Listing type** — multi-select (App / Connector / Interactive App / MCP Server / Agent).
3. **Category** — multi-select, 10 значений.
4. **Capability** — фильтр пары «capability = value». Каждая capability может стоять в одном из трёх значений: `yes`, `no`, `unknown`. UX-варианты, которые должен обеспечить фасет:
   - «есть write_actions» → `write_actions=yes`;
   - «read-only» (нет действий) → `write_actions=no`;
   - «не требует локальной установки» → `local_setup_required=no`;
   - «есть remote endpoint» → `remote_available=yes`.

   Чисто «есть/нет» (boolean) недостаточно: важно отличать «явно нет» от «мы не знаем». В фасете для каждой capability показываем три счётчика — Yes / No / Unknown — и пользователь выбирает интересующий.
5. **Pricing** — single-select (free / paid / freemium / unknown).
6. **Trust** — три независимых multi-select (см. § 6.5):
   - *Listed on platform directory* — `platform_verification_status = official`.
   - *Reviewed by LLM App Market* — `editorial_review_status = reviewed`.
   - *Verified by developer* — `developer_claim_status = claimed`.
7. **Access**:
   - `Remote available`
   - `Requires local setup`
   - `Open source`

Все фасеты отображают счётчики (сколько карточек подойдёт).

### 8.3. Сортировки

- *Relevance* (default при наличии поискового запроса).
- *Newest* — по `first_seen_at`.
- *Featured* — `is_featured DESC, quality_score DESC`.
- *Quality* — `quality_score DESC`.

### 8.4. Поведение пустого результата

Если фильтры дают 0 карточек:

- Показываем сообщение «Ничего не нашли. Попробуйте снять фильтр X.» — с кнопкой снятия последнего применённого фильтра.
- Под сообщением — 3 заранее заданных популярных запроса.

### 8.5. Подсказки в строке поиска

Под input-ом — 5 заранее заданных подсказок, рандомизируются на стороне сервера. Примеры:

- «Connect Claude to Asana»
- «Search files in Google Drive»
- «AI app for travel booking»
- «MCP server for Postgres»
- «Turn notes into slides»

## 9. Submit listing — публичный flow

### 9.1. Поля формы

- App name *
- Official website / app page URL *
- Developer / company name *
- Listing type * (ChatGPT App / Claude Connector / MCP Server / Gemini App / Other)
- Platforms (multi-select)
- Short description (макс. 280 символов) *
- Long description (макс. 4000 символов)
- Main use cases (свободные теги, до 8)
- Capabilities (чек-боксы)
- Pricing model
- Launch status
- Repository / source link (необязательное)
- Contact email *
- Capcha *

### 9.2. Что происходит после отправки

1. Запись `Submission` сохраняется в БД со статусом `pending`.
2. На email редактора уходит уведомление.
3. Пользователь видит inline-страницу: «Спасибо. Заявка отправлена, мы проверим её в течение N рабочих дней. Вам придёт письмо.»
4. Email пользователю с подтверждением и SLA («ожидайте ответ до даты»).

### 9.3. Действия редактора в Admin

- Открывает submission, проверяет URL и совпадение с описанием.
- Создаёт новый `App` (либо привязывает к существующему, если дубликат).
- Заполняет недостающие поля (verdict, use cases, capabilities).
- Меняет статус submission → `approved` или `rejected (reason)`.
- При approve — на email отправителя уходит письмо «опубликовано, вот ссылка».
- При reject — письмо с причиной + ссылка повторно отправить.

### 9.4. Rate limiting

Не больше 5 submissions в сутки с одного IP и не больше 3 в сутки с одного email. Свыше — captcha + soft-rate-limit.

## 10. Claim listing — публичный flow

Кнопка *Claim this listing* доступна на странице любого приложения, у которого ещё нет привязанного владельца.

### 10.1. Поля формы

- App slug (предзаполнено).
- Имя клеймера.
- Email на домене разработчика (например, `alice@company.com` для `company.com`).
- Ссылка-доказательство: один из вариантов
   - публичный пост в официальном аккаунте разработчика (X, LinkedIn, GitHub), где есть упоминание LLM App Market;
   - DNS TXT-запись на домене разработчика с указанным токеном;
   - запись «Claim verification: …» на репо `README.md`.
- Comment / контекст.
- Capcha.

### 10.2. Состояния заявки

- `pending` → редактор открыл, не закрыл.
- `verified` → доказательство принято.
- `rejected` → отклонено с причиной.

### 10.3. Что меняется после verified

- На карточке появляется бейдж *Verified by developer* (см. § 6.5).
- `developer_claim_status` карточки переходит в `claimed`.
- `platform_verification_status` **не** меняется автоматически: claim-ом разработчика мы подтверждаем, что человек владеет ресурсом, но это не делает карточку «official» в каталоге платформы. Эти два статуса остаются независимыми.
- Запоминается email клеймера в `App.contact_email` (для будущих обновлений).
- Клеймер получает письмо с инструкцией «как обновлять карточку» (по email через ту же форму submit, но с указанием уже существующего slug).

### 10.4. Кто финально подтверждает claim

Любая автоматическая проверка (DNS, README, email-домен) даёт только промежуточный результат — `auto_check = passed / failed / inconclusive`. Финальный перевод заявки в `verified` всегда делает редактор вручную в Django Admin. Это сознательное ограничение MVP: цена ложного «verified» (мы повесили чужой бейдж разработчика) выше, чем стоимость двух минут ручной модерации.

### 10.5. В MVP нет

- Личного кабинета клеймера.
- Возможности редактировать карточку напрямую.
- Многих клеймеров на одно приложение.

## 11. Внутренние процессы редактора

Все они выполняются через Django Admin. Никакого внешнего интерфейса для редакторов в MVP нет.

### 11.1. Очереди

В Admin доступны 3 очереди:

1. **Submissions queue** — `status = pending`, отсортировано по дате создания.
2. **Claims queue** — `status = pending`, отсортировано по дате.
3. **Drafts queue** — `App.status = draft`, авто-импорт из MCP Registry.

### 11.2. Чек-лист публикации карточки

Когда редактор переводит `App.status` из `draft` в `published`, должны быть заполнены:

- `name`, `slug`, `developer_name`
- `short_description` (≥ 60 символов)
- ≥ 1 платформа (через `AppPlatform`)
- ≥ 1 категория (через `AppCategory`)
- ≥ 3 capability-флага со значением `yes` или `no` (не `unknown`)
- хотя бы один URL: `official_page_url` или `install_url`
- `editorial_review_status = reviewed` (т.е. редактор сам подтвердил, что просмотрел карточку)
- `platform_verification_status` явно выставлен (`official` либо `not_listed`, но не `unknown`)
- если `platform_verification_status = official` — заполнен `AppPlatform.official_directory_url`
- `last_checked_at` обновлено в момент публикации

Admin показывает чек-лист как валидационный pre-check; publish-кнопка disabled, пока не выполнено.

### 11.3. Регулярная re-verification

- Cron-задача каждый день берёт 5% карточек с самым старым `last_checked_at`.
- Для каждой карточки — проверка `install_url` и `official_page_url` (HTTP HEAD).
- При 4xx / 5xx — карточка попадает в очередь *Needs review* (отдельный admin-фильтр).
- Если 7 проверок подряд возвращают 4xx/5xx — `launch_status` автоматически переходит в `deprecated`, на карточке появляется бейдж *Deprecated*, и она опускается в выдаче (через quality score). Карточка из публичной выдачи **не удаляется** автоматически: «убрать совсем» — это решение редактора (`App.status = hidden`). Это сознательное разделение: link-checker наблюдает состояние продукта в мире (`launch_status`), а решение о публичной видимости (`App.status`) принимает человек.

### 11.4. Дедупликация

При ingest и при submit система пытается найти дубликаты:

- Совпадение `slug` → жёсткий блок.
- Совпадение `developer_url` + похожее `name` (Levenshtein ≤ 3) → soft-flag.
- Совпадение `install_url` → soft-flag.

Все soft-flag-совпадения видны в Admin как «возможный дубликат, объедините».

## 12. Quality Score (внутренний)

Это число от 0 до 100, рассчитывается из заполненности карточки и качества источника. Используется для сортировки.

### 12.1. Формула (концептуально)

```
quality_score =
   +15  если platform_verification_status == official  (со ссылкой на directory)
   +10  если editorial_review_status == reviewed
   +10  если developer_claim_status == claimed
   +15  если есть official_page_url и install_url одновременно
   +10  если заполнен verdict
   +10  если ≥ 5 use cases
   +10  если ≥ 5 capabilities (с явным yes/no)
   +5   если developer_name заполнен и не "unknown"
   +5   если есть логотип
   +5   если last_checked_at < 30 дней
   +5   если есть открытый репозиторий (`open_source = true`)
   -10  если launch_status == deprecated
   -10  если карточка прошла авто-импорт и не модерировалась редактором
   -5   если за последние 7 дней ≥ 1 link-check вернул 4xx/5xx
```

Итог: clamp в [0, 100]. Заметь: статусы доверия теперь складываются — карточка одновременно «official + reviewed + claimed» получает максимальный буст; одного признака недостаточно.

### 12.2. Где используется

- Сортировка *Quality* в каталоге.
- Сортировка *Featured*: `is_featured DESC, quality_score DESC`.
- Карточки с `quality_score < 30` **не** попадают в default sort на главной (но остаются в полном каталоге).
- В админке отображается как колонка в списке App-ов.

### 12.3. Что НЕ используется

- Quality score не публикуется пользователю.
- Не показывается на карточке.
- Не влияет на наличие в выдаче (только на порядок).

## 13. Источники наполнения каталога

### 13.1. ChatGPT App Directory

- Источник: публичная страница OpenAI ChatGPT App Directory.
- Метод: ручной curated; редактор заводит карточки.
- Частота: по мере появления новых публичных приложений.
- Поле `Source.source_type` = `manual_chatgpt_directory`.

### 13.2. Claude Connectors Directory

- Источник: каталог проверенных интеграций Claude.
- Метод: ручной curated.
- Частота: ручной обход 1 раз в неделю.
- Поле `Source.source_type` = `manual_claude_connectors`.

### 13.3. Interactive Claude Apps

- Источник: подмножество Claude Connectors с интерактивным UI.
- Метод: ручной, помечается флагом `interactive_ui = true`.
- Особенность: важна выборочная проверка скриншотов и user-flow.

### 13.4. MCP Registry (автоматический ingest)

- Источник: официальный MCP Registry (REST API).
- Метод: Celery-задача `ingest_mcp_registry`, ежедневно.
- Что делает:
  1. Тянет список серверов из `/v1/servers` (с пагинацией).
  2. Нормализует поля в нашу модель `App`.
  3. Создаёт записи `App` со статусом `draft`, `platform_verification_status = official` (раз сервер числится в публичном реестре), `editorial_review_status = unreviewed`.
  4. Создаёт связи `AppPlatform` (MCP) с заполнением protocol_version / transport / repository_url из payload.
  5. Создаёт `Source` со ссылкой на запись в реестре и сохраняет полный `raw_payload`.
  6. Помечает дубликаты для ручного решения.
- Никогда не публикует автоматически — публикация только через ручную модерацию.

#### MCP Registry в статусе preview — следствия для ingest

Официальная документация MCP Registry на момент написания (май 2026) прямо предупреждает, что API находится в **preview**: возможны breaking changes схемы, ребейзы данных, ротации идентификаторов. Поэтому ingest строится с учётом этого:

- Каждый ingest-run записывает версию схемы и `fetched_at` в `Source.payload`. Если в payload пришла неожиданная схема — запись попадает в `unparsed_queue`, не ломая батч.
- Один сбойный сервер не валит весь батч: цикл ловит исключения построчно, считает успехи и ошибки.
- Retries с backoff на сетевом уровне (3 попытки, экспоненциально).
- При полном сбое (5xx подряд, недоступность endpoint-а) задача завершается, отчитывается в Sentry — следующий cron подхватит снова.
- Возможен ручной перезапуск через Django Admin: action *Re-run MCP Registry ingest*.
- При смене внешнего ID того же сервера — данные не дублируются, а сшиваются по `developer_url` + fuzzy name (см. § 11.4).
- При исчезновении сервера из реестра — карточка не удаляется молча. Помечается `Source.is_active = false`, попадает в очередь «*Vanished from registry — review*» для решения редактора (deprecate или оставить как community).

### 13.5. Submissions

- Источник: публичная форма `/submit/`.
- Особенность: всегда требует модерации.

### 13.6. Editorial picks

- Источник: ручной выбор редактора.
- Это carded apps, попавшие в подборку, на главную или в digest.

### 13.7. Что НЕ делаем


- Не импортируем сторонние списки тысяч AI-tools.
- Не используем LLM для авто-публикации.

LLM-ассистенты могут использоваться внутри редакторского процесса (например, для черновика verdict-а), но окончательное решение всегда за человеком.

## 15. Метрики продукта

Это **продуктовые** метрики (наполнение, качество, активность). Маркетинговые и финансовые метрики вне скоупа этого документа.

### 15.1. Метрики каталога

- **Количество опубликованных карточек** (`status = published`).
- **Покрытие платформ**: число карточек по каждой из 5 платформ.
- **Покрытие категорий**: число карточек в каждой из 10 категорий; ни одна категория не должна оставаться с < 5 карточками после первого месяца.
- **Trust coverage — три раздельных доли** (так как три статуса независимы, см. § 6.5):
  - доля карточек с `platform_verification_status = official` (целевое значение к концу MVP: ≥ 70%);
  - доля карточек с `editorial_review_status = reviewed` (целевое значение: ≥ 80% среди published — фактически это критерий из § 11.2);
  - доля карточек с `developer_claim_status = claimed` (целевое значение: ≥ 10% к концу MVP — claim требует усилий разработчика, 100% недостижимо).
- **Доля карточек с заполненным verdict** (целевое значение: ≥ 80% среди published).
- **Доля свежих карточек** (`last_checked_at < 30 дней`); целевое значение ≥ 90%.

### 15.2. Метрики input-а

- Количество submissions в неделю.
- Доля submissions, приведших к published (approval rate).
- Время от submit до решения (медиана).
- Количество claim-заявок.
- Доля claim-ов, приведших к `verified`.

### 15.3. Метрики output-а

- Количество карточек, которые получили хотя бы один outbound-клик за 30 дней (показатель ненулевого useful traffic).
- Outbound clicks per app — распределение, медиана, топ-10.
- CTR на блоке *Trending* / *Newly added* на главной.

### 15.4. Метрики автоматики

- Сколько драфтов сгенерировано из MCP Registry за неделю.
- Сколько из них опубликовано после модерации (approval rate автоингеста).
- Сколько карточек попало в очередь *Needs review* по результатам link-checker.

### 15.5. Что НЕ метрика MVP

- Выручка.
- DAU / MAU (в MVP трафик мал, оперируем посетителями в Google Analytics / Plausible).
- Конверсии в подписки / покупки.

## 16. Глоссарий

- **App** — единица каталога. Может быть приложением, коннектором, MCP-сервером, агентом или их комбинацией.
- **Platform** — экосистема, в которой работает App (ChatGPT, Claude, Gemini, MCP-compatible clients, Enterprise).
- **Listing type** — класс сущности (ChatGPT App, Claude Connector, Interactive Claude App, MCP Server, Gemini App, Enterprise Agent).
- **Category** — тематическая категория («Productivity», «Developer Tools», и т.д.), 10 значений на старте.
- **Capability** — структурированный флаг возможностей (read_data, write_actions, interactive_ui, и т.д.).
- **Use case** — короткая фраза, описывающая, что инструмент позволяет сделать.
- **Verdict** — одно-два предложения от редактора, объясняющих, кому и зачем нужен инструмент.
- **Platform verification status** — присутствует ли App в официальном каталоге своей платформы (`official` / `not_listed` / `unknown`).
- **Editorial review status** — проверена ли карточка редактором LLM App Market (`reviewed` / `unreviewed`).
- **Developer claim status** — подтвердил ли владелец, что это его продукт (`claimed` / `pending` / `unclaimed`).
- **Quality score** — внутренний рейтинг качества карточки, не показывается пользователю.
- **Submission** — пользовательская заявка на добавление App.
- **Claim** — пользовательская заявка на владение существующей карточкой.
- **Source** — запись о том, откуда карточка попала в каталог.
- **Draft** — карточка в статусе «не опубликована», ждёт редактора.
- **Published** — карточка, прошедшая модерацию и видимая на сайте.
- **Featured** — карточка, поднятая редактором на главную / в подборку.
- **Trending** — динамический список карточек с высоким числом outbound-кликов за окно.
- **MCP Registry** — официальный публичный реестр MCP-серверов; служит основным авто-источником для типа листинга «MCP Server».

## 17. Roadmap до MVP: три фазы

«Сразу всё» — главный риск концепции. Делим продуктовый запуск на три фазы; в каждой проверяется отдельная гипотеза. Не переходим в следующую фазу, пока не выполнены критерии текущей.

### Фаза 1 — Public Alpha (50–100 карточек)

**Гипотеза**: каталог хотя бы на короткой выборке достаточно полезен, чтобы кто-то возвращался.

Критерии готовности:

1. 50–100 опубликованных карточек, минимум по 5 на каждой из 5 платформ.
2. Работает каталог `/apps/` с фасетной фильтрацией и страницей приложения.
3. Поиск работает с typo tolerance.
4. Включены sitemap.xml, robots.txt, canonical, OpenGraph, JSON-LD.
5. Существует Submit-форма и рабочий путь от submit до published через Admin.
6. Работает базовый `MCPRegistrySource` (даёт черновики; в alpha их можно публиковать или нет — на усмотрение редактора).
7. Лендинг-страница для подписки на newsletter (без обязательного выпуска).

Что **не** требуется на этой фазе: claim-flow, рассылка, link-checker, editorial-материалы, cross-pages.

### Фаза 2 — SEO MVP (150–250 карточек)

**Гипотеза**: каталог собирает органический поисковый трафик по платформенно-категорийным запросам.

Критерии готовности:

1. 150–250 опубликованных карточек, минимум по 3 в каждой из 10 категорий и по 15 на каждой из 5 платформ.
2. Активирована схема Trust из § 6.5 — три независимых статуса заполнены у всех карточек.
3. Опубликовано ≥ 8 editorial-материалов (минимум: «What is MCP?», «ChatGPT Apps vs Claude Connectors», и 3 подборки «Best ... for ...»).
4. Включены cross-pages вида `/{platform}/{category}/` для всех пар, где ≥ 3 карточки.
5. Включён link-checker и регулярная re-verification.
6. Появилась Claim-форма, есть рабочий путь от claim до verified через Admin.
7. В Google Search Console накопились первые показы, и страницы каталога видны в индексе.

### Фаза 3 — MVP-ready (300+ карточек)

**Гипотеза**: проект превратился в работающий маховик контента и submissions.

Критерии готовности:

1. ≥ 300 опубликованных карточек, минимум по 5 в каждой из 10 категорий.
2. ≥ 15 editorial-материалов.
3. Включена и регулярно отправляется newsletter, ≥ 50 подписчиков, первый выпуск опубликован.
4. ≥ 20 самостоятельных submissions от разработчиков накоплено.
5. ≥ 5 одобренных claim-ов.
6. Доля карточек с `last_checked_at < 30 дней` ≥ 90% — link-checker работает не для галочки.
7. Включён quality score, реально влияет на сортировку «Featured» и попадание на главную.
8. Дашборд с продуктовыми метриками (§ 15) собирается из БД, а не вручную.

После Фазы 3 продукт переходит из режима «MVP-разработка» в режим «итерации на трафике». Дальнейшие фичи (отзывы, рейтинги, личные кабинеты, B2B-инструменты, монетизация) обсуждаются отдельно.
